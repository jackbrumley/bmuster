# SPEC-PRESENCE: Fast, live online and offline

**Status:** P1–P8 `IMPLEMENTED`; P9–P12 built, pending release (version bump and changelog left for the release step) · **Date:** 2026-11-07, P9–P12 2026-11-12 · Changes SPEC-ENROLMENT 8 (online rule); adds two events to SPEC-EMAIL E6.

## 1. Problem

When a machine disconnected, the console kept showing it Online for up to 15 minutes: a machine was online while its live socket was open **or** while its last check-in was within 3 intervals (3 × 300 s). The Machines list only changed on navigation. Nobody heard when a machine went offline or came back.

Every current agent holds a live socket, pinged every 30 s (a socket that misses a pong is dropped), so the socket is the fast, honest signal.

## 3. Schema (additive)

| Table      | Columns                                                                                                                                                                                                      |
| :--------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `machines` | + `socket_connected_at` (nullable: when the live socket last opened; null = never used it), + `socket_offline_since` (nullable: set when the grace ran out, to when the socket closed; cleared on reconnect) |

Who is connected, and the grace timers, live in memory (`services/agents/presence.ts`, on `globalThis` like the live-agent registry). The two columns are what a restart needs.

## 4. Routes

| Method | Path                   | Guard                                                       |
| :----- | :--------------------- | :---------------------------------------------------------- |
| GET    | `/api/machines/events` | user; every event re-checks the session and `canSeeMachine` |

`text/event-stream`: `retry: 5000` first, then `event: status` with `{ machineId, status, atIso }` (`status` is `{ kind: 'online' }`, `{ kind: 'reconnecting', sinceIso }` or `{ kind: 'offline', sinceIso }`), and a comment every 25 s so proxies keep it open. `X-Accel-Buffering: no` for nginx.

## 5. Decisions

1. **Server-sent events, not the WebSocket infrastructure.** The feed is one-way. An EventSource is an ordinary GET: it goes through the session hook and a route guard with the console cookie, like every other console request, where a browser WebSocket needs a short-lived ticket and authenticates itself outside the hooks. EventSource also reconnects by itself. The browser side lives in the one API client (`apiEvents`), parsed with a zod contract.
2. **Overlay, not reload.** A pushed status is laid over the loaded list when it is newer than the page's data (`atIso` against the load's `now`); a later reload wins. 500 machines going offline in the evening cost 500 small events per open console, not 500 reloads.
3. **Grace 60 s; restart grace 120 s.** Long enough for an agent's quick reconnect (1 s back-off at first), short enough to be honest. After a restart agents may be on their 60 s back-off, so the restart grace is twice the normal one.
4. **Offline since the socket closed**, not since the grace ran out; the Activity entry carries that time too.
5. **A socket agent stays judged by its socket.** If one later loses the socket but still checks in over HTTPS, it shows offline: sessions need the socket.
6. **Reconnecting is its own status, not a delayed Offline (P9).** The grace still keeps Activity and email quiet for blips, but the screen tells the truth at once. Reconnecting counts under the Offline filter, because no session can start on it.
7. **Context, not a second feed (P10).** One EventSource per machine page, owned by the layout. Tabs read it through a typed context (`createContext`), so a tab rendered outside the layout fails loudly instead of showing a stale status. Terminal and Desktop start or attach to their session when they mount, so their folders' `+layout.svelte` remounts them when the machine comes online or stops being online (`remount-on-presence.svelte`); Files and Storage mount their browser inside the online branch anyway.
8. **A lost session is a hint, not the truth (P11).** The session socket and the agent's live socket are separate, so `agent-lost` usually but not always means the machine went. The hint's time is the newest server time the page knows plus 1 ms, so the feed's next event or the next reload always replaces it; the 65 s check covers the case where no event comes because the machine never left.
9. **Reload on return (P12).** Rather than replay missed events, a page shown again or back online reloads once and reopens the stream.

## 6. As built (P9–P12, 2026-11-12, pending release)

- `presence.ts`: `socketClosed` publishes `reconnecting`; `presenceOf` returns it during the grace; `socketOpened` publishes `online` unless it replaces an open connection; `unreachableMessage` words the refusal in `sessions.ts` and `files.ts`.
- `StatusBadge` (amber Reconnecting), `statusLabel` in `domain/machines/machine.ts` (badge and export), `machine-row.ts` (filter, sort), Machines cards and table shortcuts, the Updates page ("reconnecting").
- `runes/machine-presence.svelte.ts` (presence, context, `announceAgentLost`), called from `SessionLink` on an `agent-lost` end; `runes/live-statuses.svelte.ts` reopens the feed on `visibilitychange` and `online`.
- Machine tabs: Overview (Last seen, Uptime, Health), Files, Storage, Terminal and Desktop read `machinePresence()`; the shared empty state is `machines/[id]/machine-unreachable.svelte`.
- Tests that render a tab on its own wrap it in `tests/helpers/presence-frame.svelte` (`underMachineLayout` in `tests/helpers/machine-presence.ts`).

## 7. As built (P1–P8, 2026-11-07)
