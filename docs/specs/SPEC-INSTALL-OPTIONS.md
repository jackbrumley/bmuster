# SPEC-INSTALL-OPTIONS: Manual install and local network mode

**Status:** `IMPLEMENTED` · approved 2026-11-07 · Part 1 (M1–M5) and Part 2 (L1–L8) built.

## Part 1: Manual install (always available)

The Add machine OS picker starts with no selection. No OS-specific command, certificate pin or download appears until the admin explicitly chooses Linux, Windows or macOS.

### Why

The one-line `curl … | sudo sh` (or `irm … | iex`) does not suit every machine: deployment tools (Intune, Group Policy, Ansible) push a file and run a command; locked-down Windows blocks piped scripts; some machines have no curl or sit behind proxies; offline networks need a USB stick; careful admins want to inspect the file first.

### Acceptance criteria

| #   | Criterion                                                                                                                                                                                                                                                                                                                              | Test                         |
| :-- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------- |
| M1  | After an OS is explicitly selected, Add machine has a collapsed **Download the agent file** section beneath its one-line command.                                                                                                                                                                                                      | `add-machine.svelte.test.ts` |
| M2  | It offers **Download agent** for the chosen OS (version, size and SHA-256 shown) from `/agent/v1/releases/<version>/<target>`. With no build on the server it says so plainly.                                                                                                                                                         | `add-machine.svelte.test.ts` |
| M3  | It shows the one command to run beside the downloaded file, with the server address and join code filled in (and the certificate pin in local network mode). Linux: `chmod +x bmuster-agent && sudo ./bmuster-agent install --url … --code …`. Windows: `.\bmuster-agent.exe install --url … --code …` in PowerShell as Administrator. | `add-machine.svelte.test.ts` |
| M4  | A "For deployment tools" note explains using one download and a roll-out join code (up to 100 machines, 7 days), with a control to make one.                                                                                                                                                                                           | `add-machine.svelte.test.ts` |
| M5  | `npm run agent:release-local` builds the agent in release mode for this computer's target and copies it to `RELEASES_PATH/<version>/<target>/`, so a dev server can offer downloads.                                                                                                                                                   | manual                       |

### As built (Part 1)

- Add machine is split into `add-machine.svelte` (join code, OS tabs, one-line command), `install-manually.svelte` (a native `<details>`, collapsed) and `rollout-code.svelte`; `+page.svelte` only passes the origin, the downloads and whether this is the dev server.
- `+page.server.ts` (admin guard) loads the newest build for each target with `agentDownload` (`services/agents/releases.ts`). The agent targets and the manual command moved to `src/lib/domain/machines/agent-release.ts`, so the page and the server share them.
- Linux offers x86_64 by default and aarch64 as an option; Windows offers `x86_64-pc-windows-msvc`. The **Download agent** link goes to `/agent/v1/releases/<version>/<target>` and shows the version and size; the SHA-256 is in a copy field. With no build it says "This server has no agent build for <target> yet." and, on the dev server only, to run `npm run agent:release-local`.
- The command beside the file appears once the page's join code exists; until then the section says to make one. macOS shows the section with "The macOS agent is not built yet."
- **For deployment tools:** the roll-out control offers 10, 25, 50 or 100 machines and 1 hour, 1 day or 7 days (presets inside the 1–100 uses and 1 minute–7 days limits of `POST /api/join-codes`, so no free-number field is needed), then shows the code, its expiry and the command with it.
- `npm run agent:release-local` (`scripts/agent-release-local.ts`) reads the version from `[workspace.package]` (or `[package]`) in `agent/Cargo.toml`, maps this computer to `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` or `x86_64-pc-windows-msvc`, runs `cargo build --release`, copies the binary to `RELEASES_PATH/<version>/<target>/` and prints the path and SHA-256.
- Tests: `src/routes/(console)/add/add-machine.svelte.test.ts` (M1–M4). M5 was checked by hand against a scratch `RELEASES_PATH`.

## Part 2: Local network mode (self-signed certificate)

### Why

Some people want BMuster only inside their home or office network, with no domain and nothing public. That means a certificate no browser or agent trusts by default.

### Acceptance criteria

| #   | Criterion                                                                                                                                                                                                                                                            | Test                                            |
| :-- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------- |
| L1  | A server setting **Local network mode** (Settings → Security), off by default.                                                                                                                                                                                       | `settings.test.ts`                              |
| L2  | Turning it on opens a confirmation explaining: the server uses its own certificate; browsers warn the first time; use only on a network you control, never exposed to the internet; agents trust only this server's certificate. The admin must tick "I understand". | `local-network-mode.svelte.test.ts`             |
| L3  | While on, every console page shows a thin banner: "Local network mode: self-signed certificate".                                                                                                                                                                     | `shell-frame.svelte.test.ts`                    |
| L4  | In this mode the server serves HTTPS itself with a certificate it makes and keeps (10 years, its LAN names and addresses as subject names), so no reverse proxy is needed.                                                                                           | `local-tls.test.ts`                             |
| L5  | Install commands (one-line and manual) include `--pin-cert sha256:<fingerprint>`; the agent then accepts exactly that certificate and nothing else, for HTTPS and the live socket. The fingerprint is shown on Add machine for checking against the browser.         | `install-scripts.test.ts`, agent `pinning` test |
| L6  | The one-line install script, in this mode, downloads with the pin as well (curl `--pinnedpubkey`; PowerShell checks the certificate hash).                                                                                                                           | `install-scripts.test.ts`                       |
| L7  | Before the certificate changes (renewal, or turning the mode off for a public certificate), the server sends every agent the new pin, or "use normal checking", over its existing trusted connection; agents switch only after confirming the new certificate works. | `pin-rollover.test.ts`                          |
| L8  | Agents never have a "trust any certificate" option outside `--insecure-dev-tls` on `enrol` and `run` for development. Turning the mode on or off is audited.                                                                                                         | review, `audit.test.ts`                         |

### As built (Part 2)

- **Setting (L1).** `localNetworkMode` (boolean, off) in `settings-definitions.ts`, with a new `section` field (`general` | `security`); the Settings page now groups settings under **General** and **Security**. Its control kind `local-network-mode` renders `settings/local-network-mode.svelte`.
- **Confirmation (L2).** Turning it on opens a modal with the four points and an **I understand** checkbox (new standard control `src/lib/ui/checkbox.svelte`, added to the hygiene list of standard controls); **Turn on** without the tick shows "Tick “I understand” to turn it on." Turning it off goes through `confirmAction`. The tick is checked in the browser only; the server records the change like any setting.
- **Banner (L3).** `ShellFrame` takes `localNetworkMode` (from the console layout load) and shows a thin warning-coloured line at the top of every page.
- **Certificate (L4).** `src/lib/server/crypto/self-signed-certificate.ts` builds the certificate with a small DER writer (`crypto/der.ts`; Node can sign and parse certificates but not build them): ECDSA P-256 (browsers refuse Ed25519 certificates), self-signed leaf (not a CA), serverAuth, ten years (backdated one hour for slow clocks), subject alternative names: the hostname, `<hostname>.local`, `localhost`, `127.0.0.1`, `::1` and every non-internal LAN address at creation time (link-local IPv6 left out). Table `local_certificates` (migration `0002`): PEM, private key sealed with `SECRETS_KEY`, pin, created. The newest row is served. Addresses that change later are **not** followed automatically; **Make a new certificate** (Settings, confirmed, audited as `local-certificate-renewed`, `POST /api/local-certificate`) picks up the new set.
- **Listener.** `hooks.server.ts` `init` decides at start-up (production only) and registers the result in `src/lib/server/tls/served-certificate.ts` (on `globalThis`, like the socket routes); `server.ts` then listens with `https.createServer` and the socket routes, or plain HTTP as before. The dev server keeps basic-ssl; `vite-plugin.ts` registers the certificate Vite serves. Changing the mode needs a restart: the toast, Settings ("Restart BMuster to apply.") and Add machine say so while what is served differs from what the next start would serve.
- **Pin (L5).** `sha256:<base64 SHA-256 of the DER SubjectPublicKeyInfo>`, the value curl's `--pinnedpubkey sha256//…` takes. The pin is computed from the certificate this process actually serves (the registered one), not by connecting to its own address: exact in dev and production, and immune to port mapping or a spoofed Host header. Add machine shows the pin and the certificate's SHA-256 fingerprint in the colon-separated hex browsers show, with a note to compare them.
- **Commands (L5, L6).** Only when the setting is on and the server serves a certificate. Linux: `curl -fsSL --pinnedpubkey 'sha256//<b64>' -k <origin>/install.sh | sudo sh -s -- --code … --pin-cert sha256:<b64>`. Windows: `& ([scriptblock]::Create((curl.exe -fsSL --pinnedpubkey 'sha256//<b64>' -k <origin>/install.ps1) -join "`n")) -Code … -PinCert 'sha256:<b64>'`(Windows PowerShell's own`irm`cannot pin, so the bootstrap uses the curl.exe built into Windows 10 and 11). Manual and roll-out commands gain`--pin-cert`. `install.sh`downloads the manifest and binary through the same pin;`install.ps1`sets`ServicePointManager.ServerCertificateValidationCallback` to compare the SPKI SHA-256 (it walks the certificate's DER to find the SubjectPublicKeyInfo, since .NET Framework cannot export it), restores the previous callback when it ends, and refuses to run under PowerShell 7, whose downloads ignore that callback.
- **Agent (L5, L8).** `install` and `enrol` take `--pin-cert`; it is saved in identity.json as `serverPin`. With a pin, all TLS (ureq HTTPS through a custom connector, and the tungstenite socket) uses one rustls verifier that accepts exactly a leaf whose SPKI hashes to the pin and ignores the host name, chain and dates; the handshake signature is still checked. Without a pin nothing changes (platform verifier). `--insecure-dev-tls` stays on `enrol` and `run` only and cannot be combined with `--pin-cert`.
- **Rollover (L7).** New socket message `{ type: 'pin-update', next: { kind: 'pin', pin } | { kind: 'public' } }`. The server sends it to every agent when its socket opens and to all connected agents when the mode changes or a certificate is made; `next` is what the next start will serve, or the current certificate when nothing is pending (which cancels an older plan). The agent stores a differing `next` as `nextPin`; when a connection under the current check fails it tries `nextPin` once and, if that works, adopts and saves it. Trade-offs: any failure (even a network outage) triggers that one extra attempt, which is harmless because `nextPin` came over a verified channel; an agent that is offline from the announcement until after the restart cannot follow and must be enrolled again; `--insecure-dev-tls` agents ignore announcements.
- **Audit (L8).** Turning the mode on or off is the usual `setting-changed` entry; a new certificate is `local-certificate-renewed`.
- **Tests:** `settings.test.ts` (L1), `local-network-mode.svelte.test.ts` (L2), `shell-frame.svelte.test.ts` (L3), `local-tls.test.ts` (L4, pin against openssl, HTTPS served), `add-machine.svelte.test.ts` and `install-scripts.test.ts` (L5, L6), `pin-rollover.test.ts` (L7), `audit.test.ts` (L8); agent: `tls::tests::pinning_*` (in-memory handshakes against openssl-made certificates), `trust::tests` (rollover), `identity::tests::pins_are_stored_in_identity_json`, protocol `pins_parse_print_and_travel_as_the_server_sends_them`. `install.ps1` was not run (no PowerShell here).
