# SPEC-DESKTOP-ALL-SCREENS: Every display at once, in one wide picture

**Status:** `IMPLEMENTED (v0.4.12)` · approved 2026-11-10 (Jack: "When someone has multiple displays … show all of them all at once in one big wide panel. … The main thing that you need that for is when you need to drag and drop a window onto a different display. So you need to drag it to the edge of the screen so that you can then continue dragging it on to the next display. We use that for a lot.") · **security work:** this changes where injected pointer input lands on another person's computer. See "As built" at the end.

## Problem

The desktop tab shows one display at a time (SPEC-DESKTOP R8). Dragging a window from one monitor to another means dragging it to the edge, switching displays and picking the drag up again, which does not work: the button is released on the switch. Support work does this all the time. SPEC-DESKTOP reserved `select-display` with `all` for this ("phase 4").

On Wayland the agent reads the screens through KMS (SPEC-CONSOLE-CAPTURE), which knows each monitor's mode but not where the compositor puts it, so displays were laid out side by side in connector order and the uinput pointer assumed that layout. With monitors stacked, offset or at different scales, clicks landed in the wrong place even on one display.

## Behaviour

1. **The choice.** The screen picker (the desktop tab's bar, the full-screen bar and the phone's floating sheet) lists each display and then **All screens**, shown only when the machine has two or more displays and the agent says it can (`allScreens` in `displays`). Choosing it sends `select-display` with `display: "all"`. The agent releases every held key and button first, as on any display switch.
2. **The picture.** The agent captures one frame: the bounding box of every display's rectangle on the desktop, each display's image drawn at its offset, black wherever no display is. The tile diff, pacing, scaling and keyframes work on it unchanged; Fit scales it to the viewer's screen. The browser shows it with the same canvas, keeping its shape.
3. **Coordinates.** Pointer positions from the browser are in the combined frame's units (the box's width and height); the agent adds the box's corner, which gives the desktop coordinates every input backend already takes. The cursor is sent in the same units. One display works exactly as before.
4. **Remembered for the session.** The choice lives in the agent's session, so a reload or reattach comes back to it (the `displays` message says `current: "all"`). When the screen at the machine changes (lock, sign-in, a user switch) and the new one can show all screens too, it opens that way. A new session starts on the primary display, as now.
5. **When the layout changes.** A monitor plugged in or out, or rearranged, sends `displays` and a keyframe. All screens stays while two or more displays remain; with one left the session goes to it.
6. **Logging.** The agent logs at info which layout it uses (mutter, side by side and why) and every display's rectangle, once per change.
7. **Limits.** A combined frame is at most 16384 pixels on a side and 8192 × 8192 pixels in all (`capture::combined::MAX_SIDE`, `MAX_PIXELS`); beyond that All screens is not offered.

### Mutter's layout and the desktop's units

- **Asking.** The agent is root. It runs `/usr/bin/busctl --user --json=short call org.gnome.Mutter.DisplayConfig … GetCurrentState` **as the desktop's user** (their uid, the group of `/run/user/<uid>`, a cleared environment with their bus address, a 2 s timeout), the way the agent's own checks reach a session bus, so root never talks to a bus the person owns. It asks only when logind says seat0 shows a `user`-class Wayland session of a uid of 1000 or more; at the sign-in screen, a text console or no session it does not ask. Which compositor to ask comes from the session's `Desktop` (see "KDE Plasma" below).
- **Matching.** Each KMS display is found among mutter's logical monitors by connector name. Mutter names HDMI type A `HDMI-n` where the kernel says `HDMI-A-n`; otherwise the names are the kernel's (`eDP-1`, `DP-2`). The monitor's current mode must equal the KMS mode. Anything that does not match falls back side by side, with the reason: a connector mutter does not list, a mode that differs, two cards with the same connector name (mutter's names cannot tell them apart), a rotated or flipped monitor, a scale outside 0.25–8, a place more than 65536 from the origin.
- **Stage.** Mutter's logical layout. In the logical layout mode (Wayland's default) a monitor of mode `w × h` at scale `s` covers `round(w / s) × round(h / s)` stage pixels; in the physical mode, `w × h`. An absent `layout-mode` means logical.
- **Desktop units: the stage times the smallest monitor scale `k`** (1 in the physical mode). Monitor edges are rounded from the stage edges (`round((edge - origin) × k)`), so monitors that touch on the stage touch on the desktop. Why: with one scale everywhere (all 100%, all 200%, all 125%) every physical pixel is kept and no image is resampled; with mixed scales one desktop unit is still the same size on every monitor, as on the stage, so the combined picture has no gaps or overlaps where monitors meet. A higher-DPI monitor beside a lower one is downscaled to match (a 2880×1800 panel at 200% beside a 1920×1080 monitor at 100% shows as 1440×900). The alternative, the largest scale, would upscale the other monitors and multiply the bytes sent for a picture that Fit scales down anyway. A single display still streams at its full mode size; only its place on the desktop uses these units, and the cursor and pointer map between the two.
- **Rereading.** Mutter is asked again whenever KMS reports a change and every 5 s while capturing (a rearrangement in Settings changes nothing KMS sees). One display is never asked about: it maps the same either way.
- **The lock screen.** GNOME's lock screen is the same mutter as the desktop, so the layout is read there too (see "Decided while building").

### KDE Plasma

**Status:** `IMPLEMENTED (pending release)` · asked 2026-11-11 (Jack's Fedora laptop runs Plasma 6 on Wayland, not GNOME) · **security work:** a second compositor whose reply moves injected pointer input.

Before this, a Plasma desktop had no mutter to ask, so its monitors were laid out side by side: wrong whenever they are stacked, offset or scaled, for All screens and for the uinput pointer.

- **Which compositor.** The agent also reads logind's `Desktop` for the session (the display manager's `XDG_SESSION_DESKTOP`). `KDE` or anything starting `plasma` means KWin; anything starting `gnome` means mutter (parts split on `:` or `;`, any case). Anything else (`ubuntu`, or empty for a session started without a display manager) is found out on the bus: `org.freedesktop.DBus.NameHasOwner` for `org.gnome.Mutter.DisplayConfig`, then `org.kde.KWin`, as the user, the first one present kept for the session. Neither present: side by side, with the reason.
- **What is asked.** `/usr/bin/busctl --user --json=short call org.kde.KWin /KWin org.kde.KWin supportInformation`, as the desktop's user, exactly as for mutter (their uid and runtime folder's group, a cleared environment with their bus address, a 2 s timeout, a 1 MB cap).
- **Why that call.** Plasma 6 has no D-Bus call that returns output geometry: libkscreen's out-of-process D-Bus backend (`org.kde.KScreen`) went with Plasma 6, and KScreen now reads the `kde_output_device_v2` Wayland protocol in process. `kscreen-doctor --json` would need starting as a Wayland client inside the person's session (their `WAYLAND_DISPLAY`, a Qt platform plugin), which is more to run as them and more to go wrong. KWin's support information is KWin's own, needs no extra package, and its "Screens" section has had the same lines since Plasma 5 (it is what KDE asks for in bug reports).
- **Reading it.** Only the "Screens" section is read (from the `Screens` heading over `=======` to the next heading); every other line in the reply is ignored, and nothing from it is kept or logged. Each `Screen N:` block gives `Name` (the kernel's connector name, e.g. `HDMI-A-1`), `Enabled` (`1`/`0`), `Geometry: x,y,wxh` (the place and size on the stage in logical pixels, already divided by the scale) and `Scale`. Outputs that are off are skipped. Refused, so side by side: no Screens section, a `Number of Screens` that does not match the blocks (a cut-off reply), a block without a usable connector name (letters, digits, `-`, `_`, at most 32), on/off, geometry (sizes 1–65536) or finite scale, more than 64 outputs, no output on.
- **Matching.** As for mutter, by connector name, plus: the stage size times the scale must be the KMS mode, give or take the scale plus one pixel (KWin rounds a logical size such as 1366/1.25 to whole pixels). A size that fits only turned sideways is a rotated monitor and falls back, as rotated monitors do under mutter (KWin's support information does not give the transform). The scale range and the 65536 limit apply as for mutter. KWin does not say which output is primary; the first display is.
- **The pointer under KWin.** KWin scales an absolute pointer to its whole workspace from 0,0 (`value × workspace / 65536`, not offset by the workspace's corner) and applies no per-device output mapping to pointers, so the same per-monitor map as under mutter lands on the right pixel when the box around the placed monitors is KWin's workspace. So KWin's layout is refused (side by side) when its workspace does not start at 0,0 (Plasma keeps it there) or when KWin lays out an output KMS does not show.
- **Rereading, logging, lock screen.** As for mutter: every 5 s and on a KMS change, logged as `Display layout from KWin` once per change; Plasma's lock screen is drawn by the same KWin in the same logind session, so its layout is the desktop's; SDDM's greeter falls back.

## Pointer mapping per backend

The browser sends a position in the shown rectangle's units; `InputController` clamps it to the rectangle and adds its corner, giving a desktop point; each backend turns that into its own absolute position.

- **X11 (XTest):** `XTestFakeMotionEvent` takes root-window coordinates, and RandR places monitors in root coordinates, so the desktop point is sent as is. Exact to the pixel on every monitor.
- **Windows (`SendInput`, `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_VIRTUALDESK`):** 0–65535 spans the virtual screen (`SM_XVIRTUALSCREEN` …), the same pixels as the monitor rectangles. The value aims a quarter of a pixel into the target (`floor((offset + 0.25) × 65536 / width)`), so Windows lands on that pixel whether its conversion truncates or rounds `value × width / 65536`; the old `(size - 1)` formula was exact only by a hair near the right edge.
- **uinput under mutter (KMS screens):** the "BMuster pointer" is an absolute device with mouse buttons and no touch or pen, which udev and libinput treat as a pointer (like a QEMU USB tablet), not a touchscreen or tablet, so mutter maps it to no single output: libinput scales it to the whole stage, `value × stage / 65536`, and mutter picks the logical monitor that holds the point. So the agent maps each desktop point **through its own monitor**: find the monitor whose desktop rectangle holds the point (the nearest one for a point in a gap, clamped to its edge pixel), take the middle of the desktop pixel, scale it into that monitor's stage rectangle, then `floor(stage offset × 65536 / stage width)` over the stage's bounding box. The point libinput gives back is at most one step (`stage / 65536`, under 0.1 pixel for a stage under 6500 pixels) below the middle of the target, so even the first and last pixels of each monitor land on it. Without mutter the map is the identity over the side-by-side places, as before.
- **Single display:** the same paths with that display's rectangle; unchanged on X11, Windows and side-by-side KMS, and now exact on a GNOME desktop whose monitors are not side by side.

## Protocol

- `select-display` `display`: an id from `displays`, or `all`. An agent that cannot show all screens (one display, too big, the portal path) answers `bad-message`.
- `displays` gains `allScreens: boolean`; `current` is `all` while all screens are shown. Older agents leave `allScreens` out; the browser reads that as false and never offers All screens to them, so an older agent never receives `all`.
- `stream` `display` is `all`; the frame header's display byte is 255 for all screens.
- No display id is ever `all`: Windows ids are `\\.\DISPLAYn`, KMS ids are `card<n>-<connector>`, and X11 ids are RandR monitor names (`DP-1`, or a name someone made with `xrandr --setmonitor`; a monitor deliberately named `all` could only be chosen through All screens).

## Security

- No permission changes: choosing a display is a view action (watch sessions may), input still needs a control ticket, and the agent enforces both as before (SPEC-DESKTOP 7). Release-all runs before the switch.
- The mutter and KWin calls (and the `NameHasOwner` checks) run as the desktop's user, never as root, with a clean environment, a fixed program path and argument list (nothing from the browser), a 2 s timeout and a 1 MB cap on what is read. The reply is only data: it moves BMuster's picture and pointer about on that person's own screen. Malformed, mismatched or out-of-range replies fall back to the side-by-side layout. The combined frame's size is capped, so no layout can make the agent allocate more than 256 MB for it.
- Pointer positions are still clamped to the shown rectangle. A point in a gap between monitors goes to the nearest monitor's edge pixel on uinput (the map does it), and X and Windows keep their pointer on a monitor themselves.

### Decided while building

- **One generic switch, three capturers.** The trait got a `View`; each platform composes in its own way (one root grab on X11, one grabber per display on Windows, one capture per CRTC on KMS) through the shared `Combined`.
- **KMS desktop units follow mutter for one display too.** The uinput pointer has always spanned all displays, so a stacked GNOME layout misplaced clicks even on one display; reading mutter fixes that whatever is shown. The KMS `DisplayInfo` rectangle can now be smaller than the image (a high-DPI monitor beside a lower one); the pointer arrives in rectangle units and the cursor is scaled from them to stream pixels, and the Fit factor is worked out from the captured image's size.
- **The lock screen reads mutter too** (the brief said fall back there). On GNOME the lock screen is drawn by the same mutter, in the same logind session, so its layout is the desktop's; falling back would move the pointer about on every lock. The sign-in screen (GDM's own mutter, as user `gdm`) does fall back.
- **Rotated monitors fall back** side by side: KMS hands over the scanout in panel orientation, and turning the image to match mutter's rectangle is not built.
- **Mirrored monitors** (one logical monitor, two connectors) get the same place; All screens draws them over each other.
- **Mutter reread every 5 s** while capturing, only with two or more displays.
