# SPEC-SESSION-FILES: Sending files through a desktop session

**Status:** phases 1 and 2 `IMPLEMENTED` (version set at release; As built: sections 10 and 11) · decisions 1–7 and all 11 open questions approved as recommended by Jack, 2026-11-15 · **Date:** 2026-11-15 · Builds on SPEC-FILES (the files channel, chunked uploads, streamed downloads), SPEC-DESKTOP section 21 (copy and paste, the KMS clipboard helper, clipboard sharing), SPEC-SESSION-UNITS (helpers in transient units), SPEC-AGENT-TRAY and SPEC-TRAY-SESSIONS (the tray in every signed-in desktop).

> **Security work** (AGENTS.md, "This tool controls other people's computers"). This spec adds a program that a root or SYSTEM service starts as the signed-in person to write into, and read from, their home folder; it puts file lists on their clipboard and reads file lists from it; it adds a ticket purpose and a channel. Every check below is in addition to the existing ones; none is relaxed.

## Open questions (with recommendations)

All eleven accepted as recommended (Jack, 2026-11-15).

1. **Does sending or fetching files also need `desktop-control`?** Recommend **yes, `files` and `desktop-control` both, in both directions, and only during a live control session of that person.** Reasons: putting files on the clipboard and reading it already needs control (SPEC-DESKTOP 21.6); a watch-only viewer has not been allowed to act on the screen, and the person at the machine consented to control, not to watch-only plus deliveries; one rule for both directions is easier to explain. Someone with `files` alone keeps the Files tab, which already reaches the whole disk.
2. **A locked screen.** The person is signed in but has stepped away. Recommend **refuse both directions while the screen is locked or at the sign-in screen**, with "The machine is locked. Unlock it, then send the files again." This matches copy and paste (C20) and means nobody receives files, or has their clipboard read, while away. Files already saved stay saved.
3. **Limits.** Recommend: **per file, the existing `maxUploadGb` setting** (10 GB by default; one setting for every upload, AGENTS.md section 10 "one path per capability"); **at most 100 files per drop**; **no total per session**, but a drop is refused when it would leave less than **1 GB free** on the Downloads disk. From the machine: **no size limit** (it streams), at most **10,000 items** in one zip and folders walked at most **32 levels** deep.
4. **Folders from your computer.** Recommend **files only in phase 1**: a dropped folder is refused with "Folders can't be sent yet. Zip the folder, or send the files inside it." Folders come later through the same helper, keeping their relative paths.
5. **Where the zip is built** (several files from the machine). Recommend **on the server, streamed**: a stored (uncompressed) ZIP64 with data descriptors, written as the agent's reads arrive, held in memory only as the existing 1 MB download buffer. The agent stays a plain reader (one read op for both single files and zips); the server hashes each file as it passes (as F5 does) for the audit. Nothing touches the server's disk. Uncompressed keeps CPU low on small servers; most large files (video, installers, archives) do not shrink anyway.
6. **The saved files' permissions.** Recommend **private to the person**: on Linux and macOS the BMuster folder is made `0700` and files `0600` (`UMask=0077`, as the clipboard helper); on Windows they inherit the Downloads folder's ACL (the person's own). The person can share them on as they like.
7. **What goes on the clipboard with the files.** Recommend **the file formats only** (CF_HDROP; `text/uri-list` and `x-special/gnome-copied-files`; file URLs), **no plain-text paths**. Ctrl+V in a text editor then does nothing rather than pasting `/home/kim/Downloads/BMuster/report.pdf`, the same on every system.
8. **Copied files while Share clipboard is off.** Recommend a **Get copied files** button in the Clipboard panel (and the full-screen sheet's Clipboard tab) that asks the machine once, as Get from machine does for text. With sharing on, Download N files appears by itself.
9. **Files copied in a Flatpak app** (the document portal's `application/vnd.portal.filetransfer`) and copies whose URIs are not local (`sftp://`, `smb://` in a file manager's network view). Recommend **later**: phase 2 reads local `file://` URIs only and says "These files are not on this machine's disks" otherwise.
10. **Windows tray notice.** The Windows tray shows no notifications today (SPEC-DESKTOP 18.4). Recommend a **notification-area balloon** (`Shell_NotifyIconW` with `NIF_INFO`), which Windows 10 and 11 show as a normal notification without registering an app id; clicking it (`NIN_BALLOONUSERCLICK`) opens the folder.
11. **Guests over share links.** Not in this spec (D14 in SPEC-SHARE-LINKS is still parked). Recommend leaving room only: the ticket purpose names the desktop session (below), so a guest version adds `route.guest` routes bound to the link's live session and no new agent code.

## 1. Problem

Helpdesk staff connected to someone's screen often need to hand them a file (an installer, a form, a screenshot) or take one back (a log, a document the person cannot email). Today that means the Files tab: a second tab, a root file browser, a path to find, and files left owned by root in a folder the person may not look in. Other remote desktop tools let you drag a file onto the screen. BMuster should too, from any browser with nothing to install, and the same on Windows, Linux (X11 and Wayland, any desktop) and macOS once a macOS agent exists.

## 3. Behaviour

### 3.1 Your computer → the machine

- **Where.** Every desktop view: the Desktop tab on a computer, its full screen, the phone page and its full-screen sheet, and the pop-out window (`desktop/window/+page@.svelte`). The drop zone is the whole stage around the picture, so a drop on the letterboxing works too.
- **Dragging over it.** When the drag carries files (`dataTransfer.types` includes `Files`), an overlay covers the stage: an upload icon and "Drop to send to <machine>", with the folder underneath ("Saved to Kim's Downloads\BMuster"). Pointer and key input to the machine pause while the overlay shows, so the drag never moves the remote pointer. The overlay goes on `dragleave` out of the stage, on `drop`, and on Escape.
- **When it cannot be used** (watch-only, no `files` permission, nobody signed in, the screen locked, the agent too old), the overlay shows the reason instead and the drop does nothing. On every desktop page a file dropped anywhere is caught (`preventDefault` on `dragover` and `drop` at the window), so a stray drop never makes the browser leave the session to open the file.
- **Upload files button.** On the session bar (computers), the full-screen bar's overflow and the full-screen sheet's Session tab (phones and tablets, where drag-and-drop is rare), shown only when sending is allowed. It opens the browser's own file picker (`<input type="file" multiple>`, no folders).
- **Several files at once,** up to 100 per drop (open question 3). They are sent one after another, each with its progress in the Transfers panel.
- **Where they go.** The signed-in person's Downloads folder, then a `BMuster` folder in it (made if missing, along with Downloads itself):
  - Windows: the Downloads Known Folder (`FOLDERID_Downloads`, which follows a Downloads folder the person moved);
  - Linux: `XDG_DOWNLOAD_DIR` from `${XDG_CONFIG_HOME:-~/.config}/user-dirs.dirs`, falling back to `~/Downloads`;
  - macOS: `~/Downloads`.
- **Who "the signed-in person" is.** The person whose session the desktop session is showing, worked out by the agent (logind on Linux, the console session's user on Windows), never named by the browser.
- **Name clashes** never overwrite: `report.pdf` becomes `report (2).pdf`, then `report (3).pdf`; a name with no extension gets the suffix at the end; a dotfile (`.bashrc`) becomes `.bashrc (2)`.
- **Resuming.** As in the Files tab: a dropped connection resumes from the part file; a part file left behind is removed by the helper after 24 hours.
- **Phase 2: on the clipboard too.** When the drop's last file is saved and Share clipboard is on, the agent puts every file of that drop on the machine's clipboard as files, so the person (or the viewer) can paste them anywhere with Ctrl+V (Cmd+V on macOS). With sharing off they are saved but not put on the clipboard, and the notice says so.
- **The browser notice** (a toast when the drop finishes): "Sent report.pdf to Kim's Downloads\BMuster on PC-12" (phase 2 adds "It's on the machine's clipboard: paste with Ctrl+V"). Several files: "Sent 3 files …". A partial drop: "Sent 2 of 3 files. report.pdf: <reason>".
- **The tray notice at the machine:** "Jack sent you report.pdf (Downloads\BMuster)", or "Jack sent you 3 files (Downloads\BMuster)". Clicking it opens the folder in the system's file manager with the files selected where the system allows it. The folder label uses the system's separator and the real folder name (`Téléchargements/BMuster` on a French Linux desktop).

### 3.2 The machine → your computer (phase 2)

- **Noticing a copy.** While Share clipboard is on, when the machine's clipboard changes to a list of files (copied in any file manager: Explorer, Nautilus, Dolphin, Nemo, Thunar, Finder), the session shows **Download N files** (one file: **Download report.pdf**) as a button on the session bar and full-screen bar, with the names and total size in its tooltip and sheet. A **cut** is treated as a copy: BMuster never removes the originals.
- **With sharing off,** Get copied files (open question 8) asks once.
- **Clicking** starts an ordinary browser download: one file as itself (with `Range`, so the browser can resume it); several files, or a folder, as `<machine> files <date>.zip`. Folders keep their structure in the zip; links inside them are skipped, never followed; anything that is not a regular file or folder (devices, sockets, pipes) is skipped and listed in the zip's `SKIPPED.txt` and in the panel.
- **The list is read as the person.** Whatever the clipboard names, the files are opened by the helper running as the signed-in person, so a file they cannot read fails with "You don't have permission to read <name> on the machine", whoever put it on the clipboard.
- **Which list.** The offer is the clipboard's list when it was noticed. A new copy replaces it; the session's end, or one hour, ends it. A file changed while it downloads ends that download with "<name> changed while it was downloading. Try again."
- **Echoes.** Files BMuster itself put on the clipboard (3.1) never come back as an offer.

### 3.3 The Transfers panel

- A **Transfers** button on the session bar (and a tab in the full-screen sheet) with a count badge while anything runs. It opens a panel under the bar, like Keys and Picture settings.
- One row per file sent and per download, newest first: direction icon, name (or "12 files (zip)"), size, a progress bar while running, then the result: "Saved as report (2).pdf", "Downloaded", "Cancelled", or the failure in plain words. Cancel on a running row; Clear finished.
- Uploads report progress from the browser; downloads from the server, which counts the bytes it streams (the browser's own download manager also shows them). The list is kept by the server in memory for one hour per person per machine, so it comes back after a reload; it is never written to the database (the audit is).

### 3.4 Who may

- **Admins and members with `files` and `desktop-control` on the machine** (open question 1), only while that person has a **live control session** on the machine's desktop, and only for that session.
- **Checked twice.** The server checks both permissions and the live session on every request (taking a permission away stops the next chunk). The agent checks the signed ticket: purpose `session-files`, permissions holding `files` and `desktop-control`, the named desktop session live on this agent, in control, for the same user id.
- **Phase 2 offers** are sent to the browser only on a desktop session whose ticket carries `files` (the agent checks), and the relay drops them towards a viewer without `files`.

### 3.5 Limits and errors

| Case                                          | Plain message                                                                                                           |
| :-------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------- |
| Nobody signed in (sign-in screen, no session) | "Nobody is signed in on <machine>, so there is no Downloads folder to send to."                                         |
| Screen locked (open question 2)               | "The machine is locked. Unlock it, then send the files again."                                                          |
| A file over the limit                         | "report.iso is 12 GB; files can be at most 10 GB (Settings → Files)."                                                   |
| More than 100 files                           | "Send at most 100 files at once."                                                                                       |
| Not enough room                               | "There isn't enough room on the machine: 3.2 GB free, these files need 4.1 GB and 1 GB must stay free."                 |
| Disk full or quota during the write           | "The machine's disk filled up while saving report.pdf." / "Kim is over their disk quota on the machine."                |
| Permission refused writing                    | "BMuster couldn't write to Kim's Downloads\BMuster folder: permission denied."                                          |
| BMuster folder is a link or not the person's  | "Kim's Downloads\BMuster is not an ordinary folder they own, so nothing was saved. Rename or remove it on the machine." |
| A dropped folder (open question 4)            | "Folders can't be sent yet. Zip the folder, or send the files inside it."                                               |
| Agent too old                                 | "The agent on <machine> is too old to receive files. Update it from the machine's page."                                |
| Reading a copied file refused (phase 2)       | "You don't have permission to read <name> on the machine."                                                              |
| Copied files not on local disks (phase 2)     | "These files are not on this machine's disks."                                                                          |

Admins see the underlying reason (the OS error) under the message; members see the message only, and the detail goes to the log (AGENTS.md section 9).

## 4. Design

### 4.1 Shape

```
browser ──HTTP (chunks, downloads)──▶ server ──session-files socket──▶ agent ──framed stdio──▶ user files helper (as the person)
browser ◀──desktop socket (offers, notices)── server (relay) ◀──desktop socket── agent / desktop helper (clipboard)
```

- **A session-files channel, owned by the server**, one per person per machine, opened on the first request and ended after 5 minutes unused: the files channel of SPEC-FILES with a new ticket purpose. Transfers never share the desktop session's socket, so a large file never holds up the picture or the keys (SPEC-DESKTOP 13).
- **The agent never decides a path from the browser.** The browser sends a file name; the helper decides the folder. Downloads name an offer id and an item number, never a path.
- **The user files helper** (`bmuster-agent user-files`) does every file operation of this spec, as the person. The agent relays frames to it unchanged, as it does for `files-helper` (SPEC-SESSION-UNITS U5).

### 4.2 Ticket purpose

```ts
| { kind: 'session-files'; desktopSessionId: string }
```

The agent requires `files` and `desktop-control` in the ticket's permissions (open question 1) and refuses the session unless `desktopSessionId` is a desktop session live on this agent, in control, whose ticket's `user.id` is this ticket's. When that desktop session ends, the agent ends the session-files session too (reason `desktop-ended`), cancelling transfers in flight and removing nothing already saved. New vectors go into `ticket-vectors.json`.

### 4.3 The user files helper

| System  | How it starts, as the person                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| :------ | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux   | A transient system unit `bmuster-user-files-<pid>-<n>.service` started with `systemd-run --uid=<uid> --gid=<primary gid>`, `NoNewPrivileges=yes`, `UMask=0077`, `stdio-host` and the connect-back socket, exactly like the KMS clipboard helper (SPEC-DESKTOP 21.10). Environment: `HOME` from the password database, `XDG_RUNTIME_DIR=/run/user/<uid>`, `XDG_CONFIG_HOME` from the person's systemd user environment if set. The uid comes from logind's record of the session on the screen (uid ≥ 1000, not 65534, not a greeter account). |
| Windows | `WTSQueryUserToken` for the console session the desktop helper is in; the linked, filtered token when it is an administrator's elevated half; the same token checks as the tray starter (SPEC-TRAY-SESSIONS, Windows step 4: a person's SID, never SYSTEM or a service account). `CreateProcessAsUserW` with `CreateEnvironmentBlock`, no window, and only its three pipe handles inherited (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`). Fixed program `bmuster-agent.exe` from the current version folder, fixed argument `user-files`.            |
| macOS   | When a macOS agent exists: `launchctl asuser <uid>` running the same program and argument in the person's GUI session, pipes as on Linux.                                                                                                                                                                                                                                                                                                                                                                                                     |

- **One helper per person per channel,** started on the first request that needs it, ended when the channel ends or the screen shows another person.
- **The helper finds the folder** itself: Windows `SHGetKnownFolderPath(FOLDERID_Downloads)`; Linux reads `user-dirs.dirs` without evaluating it: only `XDG_DOWNLOAD_DIR="$HOME/…"` or an absolute path is accepted, and a value equal to `$HOME` (the "disabled" convention) or anything else falls back to `~/Downloads`; macOS `~/Downloads`.
- **Opening the folder safely** (as the person, so the kernel's own checks apply; these are defence in depth): the Downloads folder is opened as a directory handle; `BMuster` is made in it if missing, then opened with `O_DIRECTORY | O_NOFOLLOW` (Windows: `FILE_FLAG_OPEN_REPARSE_POINT`, refusing a reparse point). It must be a real folder owned by the person (uid, or owner SID). Every later operation is relative to that handle (`openat`, `renameat2`; Windows: handle-relative `NtCreateFile` / `SetFileInformationByHandle`), so swapping a component for a link mid-transfer changes nothing.
- **Writing:** the part file `<name>.bmuster-part` is created `O_CREAT | O_EXCL | O_NOFOLLOW` (Windows `CREATE_NEW`, not through a reparse point), written at its end only, checked for size and SHA-256 at the end, as `files::transfer` does today (that code is shared, with the folder handle as its root). **Naming without overwriting:** the part file is renamed to the first free name with `renameat2(RENAME_NOREPLACE)` (Windows `FileRenameInfo` with `ReplaceIfExists = FALSE`; macOS `renamex_np(RENAME_EXCL)`), trying " (2)", " (3)" … up to " (999)" on `EEXIST`, so a file that appears meanwhile is never replaced.
- **Names from the browser** follow the strict new-name rules of SPEC-FILES F4 (one part; no `/`, `\`, `..`, NUL, `:`, control characters; Windows reserved names and trailing dots or spaces refused on every system so a file saved on Linux can go to Windows), at most 255 bytes of UTF-8. A name that fails is refused with the reason, never cleaned up silently.
- **Free space** is measured as the person (`statvfs` `f_bavail`, Windows `GetDiskFreeSpaceExW` with the person's token, so quotas count).
- **Reading (phase 2):** each path is opened with `O_NOFOLLOW | O_NONBLOCK` (Windows: without reparse following, `FILE_SHARE_READ | FILE_SHARE_WRITE`), then `fstat` must say regular file or folder; folders are walked by handle, never following links, at most 32 levels and 10,000 items. A file whose size or modified time changes between `stat` and the end of its read fails as "changed".
- **Notices to the tray:** the helper writes `<id>.json` (sender's name, file names, count, the desktop session's console session id on Windows) into the person's own private folder: `$XDG_RUNTIME_DIR/bmuster/notices/` (Linux, made `0700`), `%LOCALAPPDATA%\BMuster\notices\` (Windows). Same person both ends: no privilege boundary is crossed, and the tray treats the file as untrusted text (4.7).

### 4.4 Messages on the session-files socket

Text frames as in SPEC-FILES (`{ "id", "op", … }` → `done` / `error`), binary frames with a 4-byte request id.

| Op (server → agent)                                 | Does                                                                                                                                             |
| :-------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- |
| `target`                                            | Who is signed in and where files go: `{kind:'ready', user, folderLabel, free}` or `{kind:'refused', code, message}` (`nobody`, `locked`, …).     |
| `send-begin {transferId, name, size}`               | Checks the name, the limit and free space; makes or reopens the part file; `{partSize}`.                                                         |
| `send-chunk {transferId, offset}` + binary          | Appends at the part's end; `{partSize}`.                                                                                                         |
| `send-end {transferId, size, sha256}`               | Checks size and hash, renames to a free name; `{savedAs}` (the final name only).                                                                 |
| `send-cancel {transferId}`                          | Removes the part file.                                                                                                                           |
| `send-finish {batchId, transferIds, sender}`        | Writes the tray notice; phase 2: puts the saved files on the linked desktop session's clipboard when sharing is on; `{onClipboard}`.             |
| `offer-stat {offerId}` (phase 2)                    | The offer's items as the helper sees them now: name, kind, size, modified time; refused items with their reason.                                 |
| `offer-read {offerId, item, path?, offset, length}` | Streams one file of the offer (`path` is a relative path inside a copied folder, checked like a name for each part), with the 4 MB `ack` window. |
| `cancel`, `ack {bytes}`                             | As SPEC-FILES.                                                                                                                                   |

Error codes add `nobody`, `locked`, `not-owned` (the BMuster folder), `quota`, `changed`, `not-local` to SPEC-FILES' list. `send-finish` names transfer ids only: the clipboard gets the paths the helper saved in this channel, never paths from the server or the browser.

### 4.5 Desktop socket additions (phase 2)

| Direction | Message                                                                     | Meaning                                                                                                                                                                    |
| :-------- | :-------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| to viewer | `clipboard-files {offerId, items: [{name, kind, size}], count, totalBytes}` | Files are on the machine's clipboard (sharing on, or in reply to `clipboard-files-pull`). At most 1,000 items listed; `count` is the full number. Names only, never paths. |
| to viewer | `clipboard-files-gone {offerId}`                                            | The clipboard no longer holds that list.                                                                                                                                   |
| to viewer | `files-on-clipboard {count}`                                                | A drop's files are on the machine's clipboard (`send-finish` succeeded with sharing on).                                                                                   |
| to agent  | `clipboard-files-pull`                                                      | Ask once (Get copied files). Control and `files` only.                                                                                                                     |

The agent keeps each offer (its paths and the person's uid) in the worker's memory, keyed by desktop session; on Windows the desktop helper reads CF_HDROP and passes the list to the service over its existing pipe. `offerId` is 128 random bits. The relay drops `clipboard-files-pull` from a watch-only browser or one without `files`, and `clipboard-files` towards one.

### 4.6 Clipboard formats (phase 2)

| System                          | Putting files on the clipboard                                                                                                                                 | Reading copied files                                                                                  |
| :------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| Windows                         | Desktop helper: `CF_HDROP` (`DROPFILES`, wide paths) plus `Preferred DropEffect` = `DROPEFFECT_COPY`.                                                          | Desktop helper: `CF_HDROP` (`DragQueryFileW`); change noticed by the existing sequence number.        |
| Linux X11                       | The agent's X11 owner window (21.4) also answers `text/uri-list` (`file://` URIs, percent-encoded, CRLF) and `x-special/gnome-copied-files` (`copy\n` + URIs). | `ConvertSelection` to `text/uri-list`, else `x-special/gnome-copied-files`; XFixes watch as for text. |
| Linux KMS (Wayland or XWayland) | The clipboard helper (21.10) offers the same two types through data-control, else XWayland.                                                                    | The same helper asks for the same types; its watch reports the change.                                |
| Linux Wayland portal            | `SetSelection` offering the two types; `SelectionWrite` answers them.                                                                                          | `SelectionRead` in `text/uri-list`, else `x-special/gnome-copied-files`.                              |
| macOS (when an agent exists)    | `NSPasteboard` `writeObjects` with file `NSURL`s (`public.file-url`).                                                                                          | `readObjectsForClasses` `NSURL` with file URLs only.                                                  |

URIs are parsed strictly: `file:` scheme, empty host or `localhost`, percent-decoding to bytes, absolute paths only; anything else makes the item `not-local`. As for text, files put on the clipboard stay there only while the control session runs on that screen, unless the person copies something else or a clipboard manager keeps them; the files themselves stay in Downloads\BMuster. The agent's clipboard fingerprint (21.11 "Echoes") covers file lists, so BMuster's own push is never offered back.

### 4.7 The tray notice

- **Linux:** the tray helper, which already reads `status.json` and `viewers.json` every second, also reads its notices folder, takes each file once, deletes it, and shows a desktop notification "Jack sent you report.pdf (Downloads/BMuster)" with the default action. Clicking it calls `org.freedesktop.FileManager1.ShowItems` with the saved files (Nautilus, Dolphin, Nemo, Caja and others), falling back to `xdg-open` on the folder.
- **Windows:** the tray's balloon (open question 10); a click runs `explorer.exe /select,"<first file>"`.
- **What the tray trusts.** The notice file comes from the person's own helper, but is still treated as text: names are cleaned as `viewers.json` names are (no control characters, at most 64 characters each, at most 5 listed then "and 7 more"); files over 16 KB, malformed or older than 10 minutes are deleted unread. **The folder to open is worked out by the tray itself** (the same lookup as the helper), and only file names that exist directly inside it are selected. Nothing from the file is run or used as a path.
- **No tray helper running** (a desktop without one, SPEC-TRAY-SESSIONS open question 2): the files are still saved and the browser notice still shows; the notice file expires.

### 4.8 Routes

All `route.user`, thin, under `src/routes/api/machines/[id]/session-files/`; each checks `view`, `files` and `desktop-control` through the access service and that `desktopSessionId` is this person's live control session on the machine.

| Route                                                         | Does                                               |
| :------------------------------------------------------------ | :------------------------------------------------- |
| `GET  …/target?desktopSessionId=`                             | The overlay's text, or the refusal                 |
| `POST …/send/begin` `{desktopSessionId, batchId, name, size}` | `{transferId, partSize}`                           |
| `PUT  …/send?transferId=&offset=`                             | One chunk (at most 8 MB) → `{partSize}`            |
| `POST …/send/end` `{transferId, sha256}`                      | `{savedAs}` (audited)                              |
| `POST …/send/cancel` `{transferId}`                           | Removes the part file                              |
| `POST …/send/finish` `{batchId}`                              | Tray notice; phase 2: clipboard → `{onClipboard}`  |
| `GET  …/offers/[offerId]/download` (phase 2)                  | One file with Range, or a streamed zip (audited)   |
| `GET  …/transfers`                                            | This person's transfers on this machine, last hour |
| `POST …/transfers/[transferId]/cancel`                        | Cancels an upload or ends a download stream        |

The browser's upload queue (`upload-queue.svelte.ts`) is shared with the Files tab: it gains a destination (`{kind: 'folder', dir}` for the Files tab, `{kind: 'session', desktopSessionId}` here) rather than a second copy.

### 4.9 Schema, settings and audit

- **No database tables or migrations.** Transfers in flight and the one-hour list are in server memory.
- **Settings:** none new; `maxUploadGb` is the per-file limit (open question 3).
- **Audit kind `desktop-files`**, "Sent or fetched files through a screen", with the files icon on the Activity page. One entry per finished, failed or cancelled transfer: `direction` (`to-machine` or `from-machine`), the desktop session id, the machine, the person, the signed-in user at the machine, `completed`, the reason if not, and `items`: name (to the machine: the name saved as, and the folder label), size, bytes moved and SHA-256, for at most 1,000 items, then `count` and `totalBytes`. To the machine the hash is the one the agent checked; from the machine the server hashes each file's bytes as it passes, as F5 does. A zip entry also records the zip's own size and SHA-256. File contents are never stored or logged.

## 7. Security notes

- **Writing as the person from a root service.** Every file operation of this spec runs in the helper with the person's own uid (Linux, macOS) or filtered, unelevated token (Windows). The root or SYSTEM side never opens a path in the person's home. So the kernel is the boundary: whatever the browser sends, the helper can do only what the person's own programs can, and files are owned by them. The helper holds no agent key, ticket or credential, and is started with one fixed program and one fixed argument; the uid comes from logind or WTS, never from the browser or server.
- **No paths from the browser or the server.** Uploads carry a name, checked as one strict path part; the helper picks the folder. Downloads carry an offer id and an item number (and, inside a copied folder, a relative path checked part by part against the walk the helper did). The clipboard push after a drop names transfer ids; the agent resolves them to what its helper saved in that channel.
- **Path traversal.** Names with `/`, `\`, `..`, NUL, `:`, control characters, Windows device names or trailing dots and spaces are refused on every system (SF6). Operations are relative to the opened BMuster folder handle, so a name cannot escape it.
- **Symlink and junction tricks.** `BMuster` must be a real folder the person owns (SF5); part files are made with `O_EXCL | O_NOFOLLOW` (Windows `CREATE_NEW`, no reparse following); the rename never replaces (SF7). Since the helper is the person, a link they made could only point where they can write anyway; the checks stop a link planted by another account in a shared or group-writable home, and races between check and use.
- **The clipboard naming files the person cannot read.** Any program can put any path on a clipboard. The helper opens each one as the person, so `/etc/shadow` or another person's file fails with `denied`; `O_NONBLOCK` and the regular-file check stop a FIFO or device from hanging or leaking; links inside folders are not followed.
- **Control, files and the live session, checked twice.** The server checks permissions and the live control session on every request; the agent checks the signed ticket, the linked desktop session and its user. Ending the desktop session ends the channel.
- **The person at the machine** already sees who is connected (notice bar and tray); every delivery adds a tray notice naming the sender and the files. Nothing is sent while the screen is locked (open question 2). Received files go only to the person's own Downloads\BMuster, never a shared or temporary folder, and never overwrite.
- **The tray notice** is untrusted text even though the person's own helper wrote it: cleaned, size-capped, expired; the tray works out the folder itself and never runs or opens a path taken from the file.
- **Nothing is stored on the server.** Bytes pass through in memory (the 1 MB download buffer, 8 MB upload chunks); the zip is written as it streams. The audit records names, sizes and hashes only (SF18). File contents and the paths the clipboard named are never logged; the agent log has transfer ids, byte counts and reasons.
- **Audit.** Every transfer each way, finished or not, by who, on which machine, to or from which signed-in user, with names, sizes and SHA-256.

## 8. Manual release checks

Run each on: Windows 11 (and Windows 10), Fedora KDE Plasma (Wayland, KMS path), Fedora Workstation GNOME (Wayland), an X11 desktop (XFCE or Cinnamon), and a Wayland portal session. Check `journalctl -u 'bmuster-user-files-*'` and the agent log hold no file contents.

1. **Drop.** From Chrome and Firefox on a computer, drag three files (one with a name already in Downloads\BMuster) onto the picture: the overlay names the machine and folder; the Transfers panel shows each; the toast names them; the files are in the person's Downloads\BMuster, owned by them (`ls -l`; Explorer → Properties → Security → Owner), the clash as " (2)". The tray notice appears; clicking it opens the folder with the files selected.
2. **Pop-out and phone.** Repeat one drop in the pop-out window; on a phone, Upload files from the sheet.
3. **Refusals.** At the sign-in screen and with the screen locked, the overlay shows the reason. A watch-only session shows the reason. A dropped folder shows the folder message. A file over the limit is refused before sending.
4. **Disk full.** On a small scratch partition mounted as the person's Downloads, send a file larger than the free space minus 1 GB: refused before sending. Fill the disk during a send: the plain message, the part file removed on cancel.
5. **Links.** As the person, replace Downloads/BMuster with a link to another of their folders: refused with the `not-owned` message, nothing written.
6. **Phase 2, to the clipboard.** After a drop, paste with Ctrl+V on the desktop and in the file manager (Explorer, Dolphin, Nautilus, Thunar): copies of the files appear. With sharing off, they are saved but not on the clipboard.
7. **Phase 2, from the clipboard.** Copy one file in the file manager: Download report.pdf appears; download it and compare the SHA-256. Copy three files and a folder: one zip, opened with the system's own unzip on Windows, macOS and Linux, identical files. Copy a file the person cannot read (as root, `/root/x`, via `xclip -selection clipboard -t text/uri-list`): "You don't have permission…". Cut instead of copy: the originals stay.
8. **Audit.** Activity shows one `desktop-files` entry per transfer with names, sizes and hashes, matching `sha256sum` on the machine.

## 10. As built (phase 1, 2026-11-15)

Phase 1 (SF1–SF19) is built on the server, the browser and the agent. Linux was run in tests; Windows was compiled and linted only (`cargo clippy --target x86_64-pc-windows-gnu`), never run. Phase 2 is in section 11.

Where the build differs from sections 3 and 4:

- **Drop safety first.** Every desktop page (the Desktop tab with its full screen and phone layouts, the pop-out window, the share-link guest page) catches `dragover` and `drop` at the window (`desktop/drop-guard.ts`). Text dragged into a text box still lands there. Guests see "Files can't be sent through a share link."
- **The overlay's route is `…/session-files/destination`**, not `…/target`: the repository's ignore rule for Rust build folders (`target/`) would have kept a `target` route folder out of git.
- **Channels are per desktop session** (key `<user>/<machine>/<desktop session>`), not per person per machine, since the ticket names the desktop session and the agent ends the channel with it.
- **Part files are named `<transferId>.bmuster-part`**, never after anything the browser sent; the transfer id is the server's UUID, checked by the helper as hex and dashes.
- **The helper serves one request at a time.** Uploads are sequential anyway; a long SHA-256 check holds up the next `target` until it ends.
- **Windows folder handling:** `Downloads\BMuster` is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and must be a directory, not a reparse point, owned by the helper's own user SID. The handle is then held **without delete sharing** for the helper's life, so the folder cannot be renamed or replaced, and the files inside are opened by path with `FILE_FLAG_OPEN_REPARSE_POINT` and `CREATE_NEW`, and renamed with `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`. This replaces the handle-relative `NtCreateFile` of 4.3. The helper is this version's tray copy in Program Files (`bmuster-tray-<version>.exe user-files`), since the ProgramData version folder is not readable by the person; its stdin and stdout are the only handles it inherits (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`).
- **Who is on the screen:** Linux reads seat0's active logind session (greeter or no session: `nobody`; `lock-screen` class or `LockedHint` not `no`: `locked`); Windows reads the active console session and `WTSSessionInfoEx`'s lock flag (unreadable counts as locked).
- **`XDG_CONFIG_HOME`** is not taken from the person's systemd user environment: the helper uses its own environment's value if set, else `~/.config`.
- **Limits in the browser:** a dropped folder, more than 100 files and too little room (from the overlay's free space) are refused before anything is sent. The size limit is checked by the server on each file (the browser does not know `maxUploadGb`), so an oversized file fails in the notice with its own message.
- **Errors:** admins and members see the same message; the agent's I/O messages already carry the operating system's reason.
- **Pointer and keys during a drag:** a drag sends no pointer or key events, and the overlay covers the stage, so nothing reaches the machine; Escape closes the overlay and is not sent.
- **The Transfers panel** is on the Desktop tab's session bar only (with a running count). Upload files is on the session bar, the full-screen bar and the full-screen sheet's Session tab (phones, tablets and the pop-out window); the sheet has no Transfers tab yet, and the notices show everywhere.
- **The tray notice** on Linux uses the existing notification thread with a Show action (`FileManager1.ShowItems`, else `xdg-open` on the folder); on Windows a notification-area balloon whose click runs `explorer.exe /select,"<first file>"`.
- **Audit:** one `desktop-files` entry per transfer with `direction`, `desktop` (the desktop session id), `signed in at the machine`, `folder`, `name` (the saved name, plus `sent` when it was renamed), `size`, `bytes`, `completed`, and `sha-256` or `reason`.

## 11. As built (phase 2, 2026-11-15)

SF20–SF28 are built. Linux was run in tests (the X11 round trip skips where no Xvfb is installed, as on the build machine here); Windows was compiled and linted only.

**The main difference from 4.5: file lists never pass through a root or SYSTEM process.** Every clipboard file operation is done by the user files helper, as the person, instead of the desktop session (root on Linux, a separate helper process on Windows) watching the clipboard and pushing offers on the desktop socket:

- **Putting saved files on the clipboard (SF20):** `send-finish` carries the viewer's Share clipboard switch (`clipboard`); when it is on, the helper puts the files it saved in that drop (by transfer id) on the clipboard. Linux: Wayland data-control first (`wl-clipboard-rs`, both types), else the session's X11 `CLIPBOARD` (Xorg, or XWayland, which GNOME and other compositors bridge to the Wayland clipboard), with `text/uri-list` and `x-special/gnome-copied-files`; the display comes from the person's systemd user environment, as for the KMS clipboard helper. The portal's `SetSelection` is not used: the portal desktops (GNOME, Plasma) are reached through XWayland or data-control. Windows: `CF_HDROP` plus `Preferred DropEffect` = copy; the helper is now started on `winsta0\default`. The files stay on the clipboard while the helper lives, which is while the browser keeps asking for offers (sharing on) or 5 minutes after the last request.
- **Offers (SF22, SF27, SF28):** the browser asks `GET …/session-files/offer?desktopSessionId=` every 2 seconds while Share clipboard is on in a session that may send files, and once on Get copied files (Clipboard panel, and the full-screen sheet's Clipboard tab) while it is off. The helper reads the clipboard's file list as the person and answers with names, kinds, sizes and a 128-bit id, never paths; the same list keeps its id, a new copy gets a new one, its own push is never offered back, and an hour ends an offer (the same copy is not offered again until the clipboard changes). A list with no local files answers "These files are not on this machine's disks."
- **SF26 (who gets offers):** the offer and download routes make the same checks as sending (`files`, `desktop-control`, the person's own live control session, every request), and the session-files ticket the agent checks needs `files` and `desktop-control`. A watch-only viewer or one without `files` is never asked and never answered; nothing is relayed on the desktop socket, so there is no relay filter to test. Control desktop tickets now name `files` when the person has it (3.4), though the desktop session does not use it.
- **Downloads (SF24, SF25):** `GET …/session-files/offers/<offerId>/download?desktopSessionId=`. The helper walks the offer (`offer-stat`) by path with `symlink_metadata`, never following a link, skipping and listing devices, sockets and pipes, at most 32 levels and 10,000 items, and reads each entry (`offer-read`, by entry number, never a path from the server) on its own thread with the 4 MB read window, opening with `O_NOFOLLOW | O_NONBLOCK` (Windows: without following reparse points) and failing with `changed` when the size or modified time differs from the walk. One file downloads as itself with Range, If-Range, ETag and Content-Length; several, or a folder, as a stored ZIP64 with data descriptors and UTF-8 names (`zip-stream.ts`), with its Content-Length known up front and `SKIPPED.txt` when anything was left out. The tests unzip it with Info-ZIP, 7-Zip and Python; Windows Explorer and macOS Archive Utility were not run.
- **The session's buttons:** Download report.pdf or Download N files is on the session bar, the full-screen bar and the full-screen sheet's Session tab (pop-out window included). It is a plain link to the download, so the browser's download manager shows and resumes it. The names and total size are not shown in a tooltip; the label carries the single name.
- **Transfers and audit:** each download is a Transfers row (no Cancel: the browser's download manager cancels it) and one `desktop-files` audit entry with `direction` `from-machine`, the items with sizes, bytes sent and SHA-256, and the zip's own SHA-256.

Tests by criterion: SF20 `user_files::serve::tests` and `session-file-sender.svelte.test.ts`; SF21 `bmuster_desktop::clipboard::files::tests`, `user_files::clipboard::tests::sf21_hdrop_layout` and the desktop crate's `sf21_x11_file_list_round_trips`; SF22 and SF28 `user_files::offers::tests::sf22_…`; SF23 `bmuster_desktop::clipboard::files::tests`; SF24 `user_files::offers::tests::sf24_…`; SF25 `zip-stream.test.ts` and `session-files-download.test.ts`; SF26 and SF28 `session-files.test.ts`; SF27 `clipboard-files.svelte.test.ts`.
