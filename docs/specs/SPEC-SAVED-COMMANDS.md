# SPEC-SAVED-COMMANDS: Scripts an admin writes once

**Status:** `DRAFT` · **Date:** 2026-11-15 · Design inputs: Jack's decisions (2026-11-15), SPEC-COMMANDS (runs, the runner, the 10-at-once and 10-minute limits, recent sign-in, `run-commands`), SPEC-MCP (assistant runs held for approval, `ai-view`, `ai-commands`, the hybrid wait, section 15's "pre-approved read-only templates" risk), SPEC-ACCESS (machine groups, rules).

> **Security work.** This adds the first way for an AI assistant to run a command **without a person approving it**, and a new way for people to start a Commands run. Commands run as root or SYSTEM. Every unattended condition is checked when the assistant asks and again at each machine's turn in the runner; parameter values never become script text; the ticket and the agent are unchanged, and the agent still checks `run-commands` on its own signed ticket.

## 1. How it works

Jack wants anyone on the help desk, and their AI assistants, to check a service on a Linux server without writing a command each time.

1. **An admin writes it once.** On **Commands → Saved commands**, Ada presses **New saved command**: name "Service status", a description, a Linux script (`systemctl status "$BMUSTER_PARAM_SERVICE" --no-pager`), a Windows script (`Get-Service -Name $env:BMUSTER_PARAM_SERVICE`), the machine groups it may run on (Linux Web Servers, Corporate Laptops), a parameter `service` (short text, pattern "Service name"), the label **Reads only**, and a time limit of 30 s. She saves (her password if she signed in more than 10 minutes ago).
2. **People run it in two clicks.** Pat opens **Saved commands**, taps **Service status**, types `nginx`, ticks the machines (only machines in its groups where Pat holds `run-commands`), reviews exactly what will run, and confirms. It is an ordinary Commands run, marked "Saved command: Service status (version 3) · Reads only".
3. **Assistants use it too.** Ada turns on **AI may run this without approval**. Pat's assistant calls `list_saved_commands`, then `run_saved_command { name: "Service status", machines: ["web-1"], parameters: { service: "nginx" } }`. Because the command's AI switch is on, Pat holds `ai-commands` and `run-commands` on web-1, and web-1 is in its groups, it runs at once and the assistant gets the result. Had any condition failed, it would wait on **Approvals** like any assistant request.

## 2. Problem

Commands (SPEC-COMMANDS) needs a person to type a command each time, and every command an assistant asks for waits for a person (SPEC-MCP). Routine read-only checks (disk space, a service's status, updates waiting) are the same few scripts every time. Typing them is slow and error-prone, and approving the same harmless check over and over teaches people to approve without reading (SPEC-MCP 11.2).

## 3. Decisions (Jack, 2026-11-15) and choices made here

Jack's decisions are in the brief; this section records the choices this spec makes on the points left open.

1. **Parameters reach the script as environment variables, set by a server-made prelude.** The agent's `exec` ticket has no environment field (`SessionPurpose::Exec` is `deny_unknown_fields`) and the agent is not changed here. So the server signs a command made of a fixed prelude that sets `BMUSTER_PARAM_<NAME>`, then the admin's script, unchanged. The value is never put in the admin's script text, and the prelude's quoting cannot be broken:
   - **sh and bash:** `export BMUSTER_PARAM_SERVICE='nginx'`, in POSIX single quotes, inside which nothing is special; a `'` in the value would be written `'\''` (values cannot hold one anyway).
   - **PowerShell:** `$env:BMUSTER_PARAM_SERVICE = [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String('bmdpbng='))`. Base64 because PowerShell also treats the typographic quotes ‘ ’ ‚ ‛ as single quotes; base64 text holds only `A–Z a–z 0–9 + / =`.
   - **cmd:** not offered for a saved command with parameters (cmd expands `%` and `!` even inside quotes, and `cmd /c` reads one line). A Windows script with parameters must be PowerShell; a saved command without parameters may use cmd.
   - Values are checked against their type on the server before anything is made, and every type allows only a strict character set (section 5), so the quoting is a second line of defence, not the only one.
   - **Later:** an `env` field in the agent's ticket would remove the prelude. Recommended for a future agent release.
2. **The script text is not shown to the AI.** `list_saved_commands` gives the name, description, parameters, systems, machines, approval and label, never the scripts; results of saved command runs return `commandRun: null` and name the saved command instead. Recommended because: the description is the admin's contract with everyone who runs it; scripts can hold internal paths, host names or (wrongly) secrets, and nothing should leave for the AI provider that the admin did not write for it; and an assistant that wants a different command already has `run_command`, which a person approves. Showing the script could later be a per-command switch.
3. **Script versions: a version number plus a snapshot on the run.** Each saved command has a `version`, raised by every edit. A run records the saved command's id, name, version, label and parameter values, and its script rows hold the exact command signed into the tickets (prelude and script). No table of old versions: the run's own script row is the snapshot of what ran (the only version that matters for a run), and the audit log keeps the before and after of every edit. A content hash would add nothing the snapshot does not hold.
4. **The starter set is seeded by appended data in the generated migration**, the pattern of the built-in All machines group (migration 0006) and the Early updates and Test groups (0010, 0016). Seeded once; an admin may change or delete them, and they do not come back.
5. **Which failed condition refuses, and which goes to Approvals.** A machine without `ai-commands`, or outside the command's groups, refuses the whole call, naming the machine, as `run_command` does: no person could approve it either. A command switched off is not offered at all. The other conditions (the command's AI switch off, the server switch off, the person without `run-commands` on a machine, or the hourly cap reached) send the request to Approvals, labelled with the saved command's name.
6. **One system per assistant call**, as `run_command`: Windows and Linux machines go in separate calls, so an approval card shows one script.
7. **No Edit on a saved command's approval card.** The approver approves or denies what the saved command makes; editing would make it something other than the saved command. The server refuses an edited approval for a saved command run.
8. **An unattended run runs as the person.** There is no approver, so each ticket names the person the assistant acts as and carries their permissions, which must include `run-commands` (the agent's check, unchanged).
9. **Switched-off commands** are invisible to people and assistants; admins see them on Saved commands with an "Off" tag.
10. **Deleting** removes the saved command; past runs keep its name and version.
11. **The hourly cap** (60 unattended runs per assistant grant) is counted from the runs in the database, so a restart does not reset it.
12. **The AI access buttons** act on the group of people who may connect an assistant (`mcp.userGroupId`); they are not shown while no group is chosen.

## 5. Shapes

- **Domain** (`src/lib/domain/commands/saved-commands.ts`): parameter types as a union (`number` with `min`, `max`; `choice` with `choices`; `text` with `pattern`: `service-name` | `package-name` | `host-name` | `path` | `word`); `SavedEffect` (`reads-only` | `changes`); `composeCommand(script, parameters, values)`, pure; the env name `BMUSTER_PARAM_<NAME upper-cased>`.
- **Schemas** (`src/lib/schemas/commands/saved-commands.ts`): the saved command (form and server), the values (built from the parameter list, so the form and server check the same), the people's run request `{ version, machineIds, values, confirmCount, recheck }`, the admin's write request `{ …command, recheck }`.
- **MCP** (`src/lib/schemas/mcp/tools.ts`): `listSavedCommandsInput` `{}`, output `{ commands: [...] }`; `runSavedCommandInput` `{ command, machines (1–10), parameters: Record<string, string | number> }`, output the shared command result. `commandResultOutput` gains `savedCommand: { id, name, version, effect, preApproved } | null`.

## 6. Schema (additive)

- `saved_commands`: `id`, `name` (unique), `description`, `scripts` (JSON `[{ osFamily, shell, script }]`), `parameters` (JSON), `machine_group_ids` (JSON; a deleted group simply matches nothing), `effect` (`reads-only` | `changes`), `enabled`, `ai_unattended`, `timeout_ms`, `version`, `created_at`, `updated_at`, `updated_by` (nullable; null for the starter set).
- `command_runs` gains: `saved_command_id`, `saved_command_name`, `saved_command_version`, `saved_command_effect`, `saved_command_values` (JSON), all nullable and without a foreign key (deleting a saved command keeps its runs whole), and `pre_approved` (boolean, default false).
- Setting `mcp.savedCommandsUnattended` (default true) beside the other `mcp.*` keys.
- Audit kinds `saved-command-created`, `saved-command-changed`, `saved-command-deleted`.

## 7. Routes

- `GET/POST /api/commands/saved` (POST admins), `PUT/DELETE /api/commands/saved/[id=uuid]` (admins; DELETE behind `confirmAction`).
- `POST /api/commands/saved/[id=uuid]/plan` `{ machineIds, values }` → the exact commands, the planned machines and the sign-in check; `POST /api/commands/saved/[id=uuid]/runs` → `{ runId }`.
- `PUT /api/mcp/unattended` `{ allowed }` (admins); `POST /api/mcp/ai-access` `{ level: 'view' | 'commands' }` (admins).
- Pages: `(console)/commands/saved` (list), `(console)/commands/saved/new`, `(console)/commands/saved/[id=uuid]` (edit, admins), `(console)/commands/saved/[id=uuid]/run`.

## 8. Security notes

- **The riskiest part: unattended runs.** A tricked assistant can run any saved command with AI on, on any machine it may reach, with any value its types allow. Bounded by: admins choose which commands and label them honestly; values are typed and never script text; the person must hold `run-commands` and `ai-commands` on each machine; machine groups; one system and 10 machines per call; 60 an hour per grant; the server switch; Stop all AI access; every check again at each machine's turn; every run audited as pre-approved.
- **Reads can still leak.** A read-only command's output goes to the AI provider; admins should switch AI on only for commands whose output may leave.
- **"Reads only" is the admin's word, not a sandbox.** BMuster cannot prove a script reads only; the label is shown on every run so a wrong one is visible.
- **No widening.** The ticket and agent are unchanged; an unattended ticket carries the person's own permissions, so the agent refuses it without `run-commands`.

## 9. Out of scope

Schedules, saved commands for macOS, per-person saved commands, parameters typed as lists, showing scripts to the AI, an `env` field in the ticket (agent change), importing or exporting saved commands.
