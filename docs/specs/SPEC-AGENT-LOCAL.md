# SPEC-AGENT-LOCAL: The agent's local page and moving servers

**Status:** `IMPLEMENTED` (approved 2026-11-07; built 2026-11-07, see As built; version bump and changelog left for the release step) · **Date:** 2026-11-07

## 1. Problem

Someone at the machine (often the admin, on site) needs to see whether the agent is healthy, fix a broken connection, or move the machine to a different BMuster server, without the console and possibly without the internet. The idea comes from Wannon Beacon's on-site page; the code is written fresh.

## 2. The local page

- The agent serves `https://localhost:47500` (not 47400, which Wannon Beacon uses, so both can run on one machine) with a self-signed certificate it makes on first run. The console shows the certificate's SHA-256 fingerprint so the browser warning can be checked.
- **Localhost only by default.** A server setting can open it to the local network (for headless machines); the agent then also opens its firewall port, and closes it again on uninstall.
- **Sign-in with a 6-digit code** from the console: machine Overview → _Show local page code_ (admins only). The code changes every 30 seconds (RFC 6238 TOTP) from a secret the agent makes and sends once, inside a signed check-in. It works while the internet is down. 5 wrong codes pause sign-in for 5 minutes. A session lasts 1 hour from the last action.
- **Shows:** connected or not, server address, machine name and id, last check-in and last error, agent version and update state, CPU, memory, disks, the recent log.
- **Actions:**
  - _Test connection_: name lookup, network, HTTPS, signed check-in, each with a clear pass or fail.
  - _Check in now_.
  - _Restart the agent_.
  - _Move to another server_ (section 3).
  - _Uninstall the agent_ (with a confirmation): removes the service, the program and its identity, the same as `bmuster-agent uninstall --purge`, and tells the server it is leaving.
- `/healthz` answers without sign-in (200 healthy, 503 not), for monitoring.

## 3. Moving to another server

- From the local page: enter the new server's address and a join code from **its** Add machine page. The agent enrols with the new server first and only then tells the old server it is leaving (a signed `leave` request), so a typo never strands the machine.
- From the command line, as root or Administrator: `bmuster-agent rejoin --url <new server> --code <code>`, which does the same.
- The old server marks the machine _moved_ (not removed) in its audit log.

## 4. In the console (machine Overview, Agent panel)

Already built: the status, uninstall and uninstall-and-purge commands for the machine's system, with copy buttons.

To add:

- A **Local page** section: the address to open on the machine itself (`https://localhost:47500`, with a copy button), the certificate fingerprint to check the browser warning against, and **Show local page code** (admins): the current 6-digit code with a countdown to the next one. Viewing the code is audited.
- _Remove from this server_ (confirmation dialog): refuses the agent from now on; the agent stops.
- The `rejoin` command for moving servers.

## 5. Decisions (2026-11-07)

3. **Moving servers:** the old server marks the machine _moved_ (kept in history, refused from then on).

1. **Where it listens:** localhost only by default; the local network is an opt-in server setting.
1. **Who sees the code:** admins only for now. _Changed 2026-11-07 below: each admin sees only their own code._
1. **A code per person, and local events in Activity (2026-11-07):** each person who may sign in locally gets their own code, derived from the machine's secret, so the agent can tell whose code was used, even offline. The agent keeps the list of those people (admins today, later whoever access rules allow) from its check-in replies and reports local page events (sign-ins, wrong codes, lockouts and actions) to Activity, queued on disk while offline. Old agents keep the shared code until they are updated. Section 7.

## 6. As built (2026-11-07)

_The first version: one shared code per machine. Section 7 replaces it with a code per person._

Tested end to end against two scratch dev servers: a debug agent enrolled with the first (`--insecure-dev-tls`) and ran with `--local-page-port 47591`; in Playwright the console's Manage tab showed the code, the local page signed in with it, showed the status, passed all four Test connection steps, and moved the machine to the second server. The first server then listed no machines, recorded `machine-moved` and refused the old identity; the second listed the machine Online, checking in, and its own code signed in to the local page after the agent restarted.

### Server

- Migration `0005`: `machines.moved_at` (nullable) and table `machine_local_pages` (machine id, TOTP secret sealed with `SECRETS_KEY`, certificate SHA-256, port, reported at).
- `POST /agent/v1/leave` (signed, `{ reason: 'moved' | 'uninstalled' }`): sets `removed_at` (and `moved_at` for a move), closes the live socket as revoked, audits `machine-moved` or `machine-uninstalled` (actor System). Later requests get `revoked` with "This machine moved to another BMuster server." Lists and pages already hide machines with `removed_at`, so a moved machine is gone from them and its history stays.
- `POST /agent/v1/local-page` (signed) stores or replaces the report. A reinstall takeover deletes it (the new agent sends its own).
- `POST /api/machines/<id>/local-code` (admins): `{ kind: 'code', code, secondsLeft }` or `{ kind: 'not-reported' }`; 404 for an unknown or removed machine. POST because a view writes the audit log: `local-code-viewed` (actor the admin), at most once a minute per admin and machine (kept in memory, so a restart audits the next view again).
- Manage tab: a **Local page** section (`local-page.svelte`): the address with a copy button, the certificate fingerprint, **Show local page code** with a countdown that fetches the next code when it rolls over, and **Hide code**. Without a report: "Update the agent to get a local page." The Agent panel shows the `rejoin` command instead of "uninstall, then install".

## 7. A code per person, and local events in Activity (approved 2026-11-07)

**Status:** `IMPLEMENTED` (approved and built 2026-11-07, see As built; version bump and changelog left for the release step). Security work: it changes who can sign in to the local page and what is audited.

### Why

With one shared code per machine, the agent cannot tell who signed in, and nothing done on the local page reaches the server: a restart, a move or an uninstall at the machine leaves no trace in Activity.

### Design

- **Per-person secret.** `HMAC-SHA256(key = the machine's 20-byte local page secret, message = "BMUSTER-LOCAL-USER-1\n" + userId)`, the first 20 bytes. That is the RFC 6238 key (HMAC-SHA1, 6 digits, 30 s), the same length as the machine secret. The server already holds the machine secret (sealed), so nothing new is sent; the agent derives the same keys. A person's code says nothing about anyone else's, and the machine secret cannot be worked back from a code.
- **The list.** The server sends the agent the people who may sign in locally, `[{ userId, name }]`, sorted by `userId`: enabled admins today. The list's `hash` is the lower-case hex SHA-256 of its JSON; only the server computes it, and the agent sends it back as is. Each check-in says what the agent holds (`localUsers: { kind: 'none' } | { kind: 'held', hash }`); the reply carries the list (`localUsers: { kind: 'list', hash, users }`) only when the hash differs, otherwise `{ kind: 'unchanged' }`. The agent keeps it in `local-users.json` (0600) and uses it offline.
- **Why the list is not signed separately.** It travels in the reply to a signed check-in over the agent's checked TLS connection (trust store or pin). It can only narrow who signs in: a userId added by someone else is useless without the machine secret, and removing people is no worse than blocking the server.
- **Sign-in.** With a list, only the listed people's codes work and the shared machine code does not. Without one (an agent that has not yet heard from a newer server), the shared machine code works as before. Single use and the lockout stay per machine: a step at or before the last one used is refused whoever's code it is, and 5 wrong codes pause sign-in for 5 minutes for everyone. If several people's codes match in the same step (about one in a million per pair), the code is accepted and every matching name is recorded.
- **Old agents.** An agent that sends no `localUsers` gets no list and keeps the shared code. The server notes per machine whether the agent takes per-person codes (`machines.local_codes`, from each check-in). The Manage tab then shows each admin only their own code; for an older agent it shows the shared code and says per-person codes need an agent update. Once the agent says it takes per-person codes the server never shows the shared code for that machine.
- **Events.** The agent records local page events in `local-events.json` (0600): at most 500; when full the oldest is dropped and counted in a "dropped N" marker at the front. Each has a sequence number and the time it happened. It sends them, signed, to `POST /agent/v1/local-events` (`{ sentAtMs, events: [{ seq, atMs, event }] }`, at most 100 per request) right after an event, and after every check-in while any are waiting; the server's reply removes them. The server keeps the highest `seq` it took per machine (`machines.local_events_seq`, reset when the agent is reinstalled) and ignores anything at or below it, so a resend after a lost reply records nothing twice.
- **Event kinds.** `signed-in`, `signed-out`, `session-expired`, `wrong-code`, `locked-out` (the fifth wrong code, instead of a fifth `wrong-code`), `restarted`, `connection-tested` (passed or not), `move-started`, `move-finished`, `move-failed`, `leaving` (just before the signed `leave` of a move or uninstall), `uninstalled`, and the `dropped` marker. Each action carries whose code the session was signed in with (`{ kind: 'machine' }` for the shared code, or `{ kind: 'people', people }`).
- **Before leaving.** A move or uninstall sends the queue to the old server before its signed `leave`, because the server refuses the machine afterwards. Events still waiting after a move are deleted with the old server's list and secret.
- **Activity.** Each event is an audit entry about the machine (actor System, so members who can see the machine see it), at the time it happened, with the time it was sent in its detail. The wording names whose code: "Jack Brumley's code signed in to the local page on mint", "Restarted the agent from the local page on mint (signed in with Jack Brumley's code)". Wrong codes, lockouts and dropped events show as warnings.

### As built (2026-11-07)

- **Derivation (P1).** Agent `totp::user_secret` (ring HMAC-SHA256) and server `crypto/totp.ts` `localUserSecret`; both check `localUserCodes` in `agent/crates/protocol/tests/vectors.json`, which a third implementation (Python `hmac`) produced.
- **Protocol.** `bmuster-protocol` gains `LocalUser`, `LocalUsersHeld`, `LocalUsersUpdate` (`#[serde(default)]`, so older servers read as `unchanged`), `CodeOwners`, `LocalEvent`, `LocalEventEntry`, `LocalEventsReport` and `LOCAL_EVENTS_PATH`; `CheckInRequest.local_users` and `CheckInReply.local_users`. The server's zod check-in schema defaults a missing `localUsers` to `{ kind: 'unsupported' }`.
- **The list (P4).** `access.localPagePeople` (enabled admins in id order, through `users.enabledAdmins`) is the one place that decides who is on it; `agents/local-users.ts` hashes it and answers the check-in. Each check-in sets `machines.local_codes` (`shared` | `per-person`), so a downgraded agent goes back to the shared code. Migration `0007` adds `local_codes` and `local_events_seq`; a reinstall takeover resets both.
- **Agent (P5, P6).** `local_page/people.rs` keeps `local-users.json` (0600, written before use). A list that cannot be read lets nobody in (never back to the shared code) and is reported as none held, so the next check-in resends it. `gate.rs` checks every listed person's own key (three steps each); sessions remember whose code it was and end when that person leaves the list or a list replaces the shared code. A sweep every minute ends idle sessions so their end is recorded near when it happened. The status page shows "Signed in with Bea Second's code", and the log names whose code signed in.
- **Events (E1, E2).** `local_page/journal.rs` keeps `local-events.json` (0600). Sequence numbers start from the clock in milliseconds (`max(next, now)`), so a lost file or a new install still numbers above what the server has seen. The page sends on a background thread after each request that queued something; the check-in loop sends after each successful check-in, and after a refusal (an older server) waits an hour. Sends are serialised. A move sends the queue to the old server just before its `leave` (a new `before_leave` hook on `relocate::move_to`, also used by `rejoin`), and `finish_pending_move` deletes `local-users.json` and `local-events.json` with the old secret. The server corrects each event's time by the gap between the report's `sentAtMs` and its arrival, never later than the arrival.
- **Manage tab (P2, P3).** `POST /api/machines/<id>/local-code` replies `{ kind: 'code', code, secondsLeft, scope: 'person' | 'machine' }`, or `not-listed` for someone not on the list. The view's audit detail says `code: their own` or `shared`. The panel says "Your own code: …" or, for an older agent, "A shared code: every admin sees this one, so Activity cannot say who used it. Update the agent to give each person their own code."
- **Activity (E3).** Thirteen new audit kinds (`local-signed-in` … `local-events-dropped`), actor System, about the machine. `domain/activity/local-page-activity.ts` words them; the Activity page shows that sentence, a warning icon for wrong codes, lockouts, failed connection tests, failed moves and lost events, and "Reported by the agent …, after it was offline" when an event arrived more than 2 minutes after it happened.
- **End to end (E4).** A scratch server built from this branch on `127.0.0.1:47650` (fresh database, explicit `DATABASE_PATH`, `RELEASES_PATH`, `SECRETS_KEY` and first-admin variables, `PROTOCOL_HEADER=x-forwarded-proto` so plain-HTTP form posts pass the origin check) and a debug agent enrolled with `--insecure-dev-tls`, run with `--local-page-port 47651`. A second admin (Bea Second) was added. In Playwright, Bea's Manage tab showed "Your own code"; the agent's local page signed in with it and showed "Signed in with Bea Second's code"; Restart worked; Activity read "Bea Second's code signed in to the local page on e2e-mint" and "Restarted the agent from the local page on e2e-mint (signed in with Bea Second's code)". The shared machine code was refused ("That code is not right"), recorded as a warning. With the server stopped, Bea's code signed in and Test connection ran (failed); both waited in `local-events.json`; 45 s after the server came back they were in Activity at the times they happened, and the queue was empty. Ada's code differed from Bea's. Checked at 390 px in dark mode.
- **Not done or not verified.** An older agent against this server (the compatibility path is unit-tested only: a check-in without `localUsers` gets no list and keeps the shared code). Moving and uninstalling with events waiting (unit-tested ordering only). A full 500-event queue against a server. The `npm run agent:dev` script was not used, because it cannot pass `--local-page-port` and expects the binary in `agent/target`; the same steps were run by hand.
