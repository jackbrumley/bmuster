# Engineering plan

What BMuster takes from the Wannon Digital portal's engineering discipline, and in what order. The portal is a large multi-tenant SaaS; BMuster is a single-tenant, self-hosted tool. We copy the rules and checks that keep code clean and fast to change, and leave the tenancy, billing, AI and support machinery behind.

## 1. Repository layout

```
bmuster/
  src/                      SvelteKit app: web console, API, agent endpoints, relay
    lib/
      server/               server-only: database/, env.ts, services/<area>/, guards/, hooks/, sockets/
      domain/<area>/        browser-safe types and pure rules (machines, activity, …)
      schemas/<area>/       zod request and reply contracts
      ui/                   tokens and shared components
      shell/                app frame (sidebar, tab bar)
      utils/                formatting, the one API client
      prototype/            made-up data for the UI prototype (deleted when real data lands)
    routes/                 thin: validate, call a service, reply
  scripts/                  hygiene, verify, migrate (plain Node, type stripping)
  tests/                    unit/, ui/, hygiene fixtures
  agent/                    Rust: the program installed on each machine
  docs/                     concept, specs, this plan
```

`src/lib/` holds only folders. Route-only components sit beside their route.

## 2. Already in place (2026-11-07)

- SvelteKit 3, Svelte 5 (runes everywhere), Vite 8, adapter-node, TypeScript 6.
- Exact dependency versions (`save-exact`), `engine-strict`, Node ≥ 26.
- `tsconfig.json` with the portal's strict flags (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, …).
- `eslint.config.js` with the portal's rules: `strictTypeChecked`, no inline disables, `strict-boolean-expressions`, `switch-exhaustiveness-check`, no object-literal assertions, keyed `each`, no `{@html}`, `no-console`.
  - One difference: `svelte/no-navigation-without-resolve` stays **on**. Links go through `resolve()`, which type-checks every route and lets self-hosters serve BMuster under a sub-path.
- Prettier: tabs, single quotes, no trailing commas, width 100.
- Vitest projects `unit` (Node) and `ui` (browser), with `requireAssertions`, `restoreMocks`, `unstubEnvs`, `unstubGlobals`.
- Drizzle + SQLite (better-sqlite3), WAL mode, foreign keys on. Env read only through `src/lib/server/env.ts`, fail hard when missing.
- Design tokens in `src/lib/ui/design-tokens.css`: spacing, type, radius roles, safe areas, light and dark themes.
- Dev server on HTTPS and the LAN for phone testing.

## 3. Rules to write into AGENTS.md

Adopt as-is (portal section in brackets):

- No destructive database commands by agents; only `db:migrate` locally. (top)
- Start from the latest code: fetch, compare, fast-forward only. (top)
- Thin routes, under 200 lines: validate, call a service, reply. (§5)
- Server boundary: `src/lib/server/**` never imports `$app/*`; browser code never imports server code. Shared shapes live in `lib/domain/`. (§5)
- No `any`, no `as unknown as T`, no `x!`; parse untrusted input with zod. (§6)
- No lint or type bypasses of any kind. Loosening a lint rule is a reviewed change. (§6)
- TypeScript that Node runs directly: no `enum`, no `namespace`, `.ts` import extensions, `import type`, `#lib/*`. (§6)
- Runes discipline: `$derived` not synced `$state`; `$effect` only for DOM and outside systems. (§6)
- File size: split at 600 lines, fail at 1000. (§6)
- Exact versions only. (§6)
- Never push on your own; never discard someone else's changes. (§7)
- Fail hard: no silent fallbacks. (§8)
- Simplicity first; delete before adding. (§9)
- Zero shims: no re-export facades, no translation layers; JSON camelCase, database snake_case. (§11)
- One API client in the browser with a zod reply contract; toasts and `confirmAction`, never `alert()`/`confirm()`. (§13)
- Compiler-driven refactoring: make it mandatory, let `check` list the work. (§14)
- Discriminated unions, no optional props; shared components take no `class`/`style`. (§16)
- Tabler icons only, no emoji. (§4)
- Zero tech debt: one path per capability, dead code removed in the same change. (§22)
- Server owns the run: sessions and scans live on the server; browsers are viewports that re-subscribe. (§24)
- Scoped styles, tokens only; surface roles; radius roles (pills to click, boxes to type in); page frames own safe areas; 16px minimum in fields (iOS zoom). (§3)

Adapt:

- **Database** (§2): TS-first Drizzle schema split by area under `server/database/schema/`; server-made UUIDs; additive migrations generated by drizzle-kit, never hand-edited; migrations run at start-up.
- **Guards** (§27): `route.public`, `route.user`, `route.role(role)`, `route.agent` (agent token). The handler context holds only what the guard proved.
- **WebSockets** (§27.4): socket routes with tickets for browsers; agents authenticate with their own signed credential, never a cookie.
- **Service areas** (§29): `agents`, `sessions`, `inventory`, `users`, `auth`, `settings`, `audit`. Two layers (foundation, feature); repositories touch only their own tables.
- **Tests** (§20): one in-memory SQLite database per test file instead of the portal's mock and real split. Seed your own rows.
- **Records** (§26): data table, then view modal, then edit modal.
- **Plan, then implement** (Definition of Done): spec, approval, tests first, implement, verify.
- **Changelog and versions** (§7): semver bump and `changelog.ts` per change.

Skip: tenancy and SaaS isolation, staff vs customer, Stripe, AI, help articles, support API, graphify, i18n, product registry, Capacitor.

## 4. Hygiene and verify (to port)

Copy from `portal/scripts/` and trim. Each rule is registered in `rules.ts` with its section, why and fix; an unregistered rule id fails `check`; every rule has a bad and a good fixture.

| Port first                                                                                                     | Purpose                                                                          |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `hygiene.ts`, `rules.ts`, `report.ts`, `rule-index.ts`, `source-file.ts`, `template.ts`, `imports.ts`, `fs.ts` | Runner, registry, reporter, parsers                                              |
| `file-layout.ts`                                                                                               | kebab-case, `lib/` root has no files, file size                                  |
| `code-standards.ts`                                                                                            | bypass comments, `any`, inline deps, keyed each, raw HTML (minus the staff rule) |
| `styling.ts`, `css-values.ts`, `border-radius.ts`                                                              | tokens only, no `!important`, radius roles                                       |
| `page-frames.ts`, `input-font-size.ts`                                                                         | safe areas, 16px fields                                                          |
| `server-boundary.ts`, `double-cast.ts`, `client-fetch.ts`, `env-vars.ts`                                       | layering and safety                                                              |
| `raw-controls.ts`, `destructive-confirmation.ts`, `ui-components.ts`                                           | UI discipline                                                                    |

Later: `routes.ts` (guard required, no DB in routes, validation), `route-tests.ts`, `service-areas.ts`, `service-layers.ts`, `database.ts`, `file-transfer.ts`, `settings-registry.ts`.

Also port:

- `knip` (dead code, `treatConfigHintsAsErrors`) and `jscpd` (duplication: 10 lines or 100 tokens).
- `scripts/verify.ts`: runs lint, check, format, hygiene, dead code and duplication in parallel, then tests and the build; prints one pass/fail table. Flags `--fast` and `--skip-if-verified`.
- `scripts/verify-stamp.ts`: skips a re-run when the working tree and Node version are unchanged since the last pass.
- `.githooks/pre-push`: `npm run verify -- --fast --skip-if-verified`, installed by `prepare`.
- A design-token generator (`design-tokens.ts` → `.css`) with a staleness test, once the token set settles.

The Rust agent gets its own gate: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, run from `verify.ts`.

## 5. Database: SQLite and Drizzle

- **SQLite.** One file, nothing to install, backups are a file copy, and it runs well on a Raspberry Pi. The write load is small: a few hundred machines checking in every minute is a handful of writes per second, well within SQLite in WAL mode.
- **Drizzle.** The same schema-in-TypeScript workflow as the portal. `drizzle-kit generate` makes migrations from schema changes, and SQLite's `ALTER` limits are handled by drizzle-kit rebuilding the table.
- **Fast change without refactors.** Keep every query inside its area's repository. If Postgres is ever needed (many hundreds of machines, several server instances), only the schema files and repositories change.
- **What stays out of the database.** Live figures (CPU and memory every few seconds) stay in memory and stream to the browser. The database keeps inventory snapshots, sessions, audit entries and down-sampled history.
- **Driver.** `better-sqlite3` for now. Drizzle 1.0 adds Node's built-in `node:sqlite`, which removes the native build; switch when 1.0 is stable.

## 6. Order of work

1. UI prototype with made-up data (done: machines, machine overview, terminal, desktop, files, add machine, activity).
2. AGENTS.md with the rules in section 3. CLAUDE.md is a link to it.
3. Port hygiene, verify, knip, jscpd and the pre-push hook.
4. Specs: enrolment, check-in and inventory, session relay.
5. Server: database schema, guards, agent endpoints, socket relay.
6. Agent: Rust workspace in `agent/`, launcher and worker, enrolment, check-in.
7. Terminal sessions end to end, then desktop, then files.
